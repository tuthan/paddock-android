# Saved machines: watch another, remove one

Paddock saves every machine the user adds and **watches one at a time** (`AppSettings.watchedProfileId`). Adding a machine saves it and makes it the watched one, as before; adding the same host, port and user again updates that profile. This page is what the saved machines get (2026-10-06, the user's decisions): a **Machines** screen and a page for each machine, **watch another one (Pro)**, **wake any of them (Free)**, **remove one (Free)**, and a chip for each machine on Home.

## The machine list

**Machines** (`MachinesScreen` in `ui/screens/Machines.kt`, `Route.Machines`) is a screen, not a dialog. It opens from the watched machine's chip on Home and from the **Machines** row in Settings ("2 saved · watching Laptop", `MachineCopy.settingsRow`), and Back returns to whichever opened it. Neither it nor a machine's page shows the bottom bar. Under the header, one line: "Paddock watches one machine at a time. Open a machine to watch it, wake it or remove it." (`MachineCopy.INTRO`), then, for a phone without Pro that an alert moved off the chosen machine, the displaced line (below). Then one card per saved machine, the watched one first and the others in the store's order (by name, `MachineRoster.rows`):

- the machine's OS glyph (Linux, macOS or Windows, 24 dp, when one is known; see "Name and icon" below), the name (`rowTitle`, not the header style), then `user@host:port · session <name>` (or `· default session`) dim, then a state line: for the watched machine **Watching · live**, **· connecting** or **· not live** in the accent colour (the same health as Home's chip, `chipHealth`), and for any other **Not watched**, then what the phone knows: **· wake ready** (a hardware address is read and a packet can be sent from this network: `AppGraph.wakeReady`), **· wake not read** (nothing read yet) or **· wake not available** (read, but no packet can leave from here), and **· alerts set up** when a UnifiedPush registration with an address exists for it on this phone (`MachineCopy.otherLine`, `MachineRoster.wakeWord`);
- a chevron; the whole card is one button ("Open <name>") that opens the machine's page;
- on every card that is not watched, one small Secondary **Watch**, so a switch from Settings takes two taps (the Machines row, then Watch) without opening the machine's page. Locked (below), it draws the lock glyph and the "Pro" tag (`PaddockButton(pro = true)`) and TalkBack reads "Watch Beta server · Pro"; the free return to the chosen machine is a plain Watch. Which Watch is locked is one rule for the card, the page and the chips (`MachineRoster.watchLocked`).

**Add another machine** (Ghost) opens Add a machine, and Back from there returns to Machines. There is no Remove on the list: it is on the page, one tap further, behind its confirmation. The list is `AppGraph.machines`, read from the profile store at start, after an add and after a removal, and updated in place when a machine's wake reading or relay is written (`machineWritten`), so the state lines follow without a re-read.

### A machine's page

`MachinePage` (`Route.Machine`, `MachineRoute` in `PaddockRoot.kt`) has the machine's name as its header and five sections:

- **This machine**: Address (`user@host:port`) and Session as facts, then the state line. The watched machine's line is drawn as the accent chip ("Watching · live"), so "Watching" is not said twice; any other has its state line and a **Watch** (Secondary; locked as on the list, plain for the free return).
- **Name and icon**: the name field with **Save name**, and the **Icon** row (below). Free for every saved machine.
- **Wake-on-LAN**: the same section Settings had (`WakeOnLanSection` fed by `WakeWordsMapper.words` for this machine): what was read, the commands to copy, the relay field, **Wake the machine** and the last tap's lines. Free for every saved machine, watched or not (decision D2; `docs/wake.md`, "Waking a machine that is not watched").
- **Locked-phone alerts**: one line from this machine's UnifiedPush registration on this phone, in the relay screen's own words (`PushWords`: "The address is on <machine>.", "The distributor gave this phone an address. It is not on <machine> yet.", "Registration failed. Register again.", or "No UnifiedPush registration for this machine on this phone."). For the watched machine a row **Set up or check…** opens the alert relay screen, and Back from there returns to the page. Another machine says "Watch this machine to set up or check its alerts." and has no row: that screen reads the machine through the live connection. **Alerts for a machine that is not watched still arrive** (each machine has its own relay and address), and a tap on one switches the watch to it, free; while Paddock is open only the watched machine's own alerts are skipped, since only its herd is on screen (`alerts.md`, "Several machines").
- **Guarded answers** (2026-10-07, the user's request; it was a row of Settings): one line saying what they are, then **Set up guarded answers…** on the watched machine, which opens the setup screen (`GuardedAnswersRoute`; since the same day it covers Claude Code, Codex and opencode, `guarded-answers.md`) for it; **Pro**, so a locked phone reads "Set up guarded answers… · Pro" and the tap asks the gate first, as the Settings row did. Another machine's page says "Watch this machine to set up or check its guarded answers." (`MachineCopy.GUARDED_WATCH_FIRST`) and offers nothing. Back from the setup returns to this page. Settings keeps one line under Sending: "Guarded answers … are set up per machine: Machines, then the machine's page."
- **Remove**: **Remove…** (Danger), below.

### Home's chips

With **one** saved machine Home keeps its single chip (`HostChip`): the health dot, the name and a small caret (`PaddockIcons.Chevron` turned down, 14 dp; the machine icon it had only repeated what the chip already says), then the dashed status chip ("live · 3 s"). A tap opens Machines. TalkBack reads it in the row's words for the watched chip ("Alpha, watching, live · 3 s", `MachineCopy.chipWatched`), so adding a second machine does not change how the same chip sounds; Spaces' chip, the same `HostChip`, reads the same. With **two or more**, Home draws `MachineChipRow` (the design's `.chips` row, `Main.body.html`): one line with the watched machine's chip first, drawn exactly as the single chip (a tap opens Machines; TalkBack: "Alpha, watching, live · 3 s"), then every other saved machine in the store's order as a plain chip (the `surface` fill, the control line, a neutral `faint` dot because its health is not known here, the name, and a 14 dp lock after the name when the switch is Pro for this phone and it is not the free return; TalkBack: "Beta, not watched" or "Beta, not watched, Pro"), and the dashed status chip last (its words are already in the watched chip's name, so TalkBack does not read them twice). The status chip is pinned outside the scrolling machine chips: only the machine chips scroll, so with three machines on a narrow phone how fresh the screen is never scrolls off the edge, and when the chips fit it sits right after the last one. A tap on another machine's chip asks to watch it through the same rule as the list and the page. Every chip is a button with a 48 dp target.

### What a chip says about its machine (Pro, `hosts.merged`)

With Pro, a chip for a machine that is **not watched** says after its name how many agents on it need you, and how old that look is: "Beta server · 2 need you · 20 s ago" (`ChipGlance.text`, in the attention colour only when the count is above zero; the words carry the meaning), "all clear · 8 s ago" for none, "1 needs you" for one. TalkBack reads it between the watched state and Pro: "Beta server, not watched, 2 agents need you, read 20 s ago" (`MachineCopy.chipOther`). A tap still asks to watch it, by the same rule as before; there is no second queue: the herd, the Yes/No sheet and the alerts' targets stay the watched machine's. The watched chip never carries a count (it is the live one), and a chip with nothing read yet is just its name.

**How it is read** (`MachineProbe`, core, no Android): a light look at each machine that is not watched, **only while Paddock is in front and not covered by the app lock**, every 30 s per machine. One look opens one short SSH session with the machine's own key and pins (not the owner's connection: no lease, no heartbeat), locates herdr, runs `herdr session list --json` and `herdr --session <the machine's session> agent list`, counts the agents whose status is `blocked`, and closes the session. It reads: no install, no write, no key sent, no stream. At most two looks run at once, and each has a 25 s deadline, connect included.

- **It never asks.** A look declines an unknown host key (`connectForProbe`: `{ false }`) and records no changed-key warning, so a machine whose key this phone has not trusted yet, a changed key, a refused sign-in, an unreadable key or a missing local-network grant reads **"open to check"** instead of raising a prompt over Home. Tapping the chip watches the machine and meets the real prompt, as always.
- **A failure says so, and keeps the last count.** "not reachable" (asleep, off the network, refused, timed out), "herdr not available", "no session to read" (none running, or several and none chosen for that machine) replace the count on the chip; the spoken name keeps what was last read: "Delta, not watched, not reachable; last read 3 min ago, 3 agents need you". A count that may be old is never drawn in the attention colour.
- **A failing machine is looked at less and less often.** Unreachable: 30 s, 1, 2, 4 min, then every 5 min; the other three problems wait 5 min, because nothing there changes by itself. A network change and a return to the front look again at the next tick; leaving for the background looks no more (`run-probe-e2e.sh`: no new login at the sshd in 85 s away, a new one within 45 s of the return).
- **Without Pro nothing is looked at** and a count read while Pro was held is not drawn (`graph.locked(HOSTS_MERGED)`); push alerts for every machine arrive on Free either way.
- **Removing a machine** forgets its readings (`MachineProbe.forget`).

**Tests.** `core`: `MachineProbeTest` (13: counts blocked agents of the real herdr 0.9.1 fixtures and no other state, sends only the three read commands and asks for the machine's own session, unreachable keeps the last reading, every connect failure that needs the user reads "open to check", no herdr / no session / several sessions, a look that never answers is closed at its deadline, a good look is not repeated before the interval, a restart does not look twice, `lookAgainNow`, at most two at once, cancel closes sessions, forget), `ProbeCopyTest` (the chip's words and spoken name, the cadence, which machines are looked at: in front, unlocked, Pro, never the watched one). Instrumentation: `MachinesTest` (a chip's count and age, TalkBack name, a machine that could not be read, the watched chip never carries one, a tap still watches, contrast audits dark, light and at 200 %). Device: `paddock-harness/run-probe-e2e.sh` (`ProbeFlowTest`, two machines on one host: the other chip counts the blocked agent, follows it to idle and back, no login while the app is in the background, a look again on the return, no key sent, a tap on the chip watches that machine and the first one becomes the chip). **Not verified:** a real phone, a real second machine on another network, a Mac, TalkBack on the chips, a machine whose host key is not trusted yet (the "open to check" path is tested with the failure injected, not against a real unpinned key), Pro lost mid-session on a Play build.

## Name and icon (2026-10-07, the user's request)

A saved machine has a **name** the user can change and an **OS icon** (Linux, macOS, Windows) that says what kind of machine it is. Both are in a **Name and icon** section of the machine's page, after the address, the state line and Watch (the things the page is mostly opened for), and both are Free for every saved machine, watched or not.

### Name

**Name on this phone** is a text field filled with the current name, and a Secondary **Save name** (`NameEditor`, `MachineName`). The words under it say what it is: "Shown on Home, in the list and in alerts. It is only a label on this phone: nothing on the machine changes." (`MachineCopy.NAME_HINT`), because the name is the profile's own `name` and never reaches the host, the session or herdr.

- **Rules** (`MachineName.check`, then `HostProfile`'s own check as the last word): trimmed, 1 to 60 characters, no control characters, and not the name of another saved machine, compared without regard to case so two cards are never told apart only by a capital. Save is off until the text is a name that passes and differs from the saved one; the error shows only once the text differs, so an untouched field is quiet. The keyboard's Done saves too.
- **The id does not change.** `AppGraph.renameMachine` rewrites the profile in place (`profiles.update(id) { copy(name = ...) }`), so everything keyed by the id stays attached: the trusted host key, the ledger, the alert registration, the wake facts, the chosen-machine record and the `h` an alert carries. The alert's title and Home's chip use the new name from the next frame.
- **Renaming the watched machine reconnects once**, because the live connection carries the profile (`watch()` compares everything except the wake, OS and icon fields). Renaming another machine touches no connection. A rename says "Renamed to <name>." (`MachineCopy.renamed`).

### Icon

The card, the page and (with two or more machines) Home's chips draw a small glyph before the name: a penguin outline for Linux, an apple for macOS, a window of four panes for Windows (`PaddockIcons.Linux`, `MacOs`, `WindowsOs`, `forOs`). The glyph is decorative beside the name on a chip; on a card and on the page TalkBack reads "Linux machine" (`MachineCopy.osSpoken`). With one machine Home keeps its single chip without a glyph, as before.

Where the answer comes from, in order:

1. **The user's pick** (`HostProfile.os`): the page's **Icon** row is an option row (Automatic, Linux, macOS, Windows). A pick is kept until the user changes it, even when the machine later says something else.
2. **What the machine said** (`HostProfile.detectedOs`): at every bring-up of the watched machine, over the connection already open, Paddock runs the one constant command `uname -s 2>/dev/null` (`HostOsProbe`, `HostSessionController.probeOs`, 5 s limit, nothing interpolated and nothing written) and reads `Linux` as Linux, `Darwin` as macOS, and `MINGW64_NT-…`, `MSYS_NT-…` or `CYGWIN_NT-…` as Windows. The answer is saved on the profile (`saveDetectedOs`) only when the stored profile is still that host and port, and a change is written once, not on every connect. Automatic shows what was read: "Automatic (macOS)".
3. **Nothing:** a machine that has not connected since this arrived, a host that did not answer, or a BSD or any other `uname` output has no glyph, and the page says "Not known yet". Nothing guesses.

What this does **not** do:

- **A Windows machine whose SSH shell is PowerShell or cmd is not detected** (`uname` does not exist there), so it shows no glyph until the user picks Windows. Paddock's host features (herdr, tmux, the relay's systemd unit, the wake capture) need a Unix shell on the host in any case; Windows works through WSL, MSYS2 or Git Bash, and a WSL host answers `Linux`, which is what the machine is for Paddock's purposes.
- **Only the watched machine is probed.** A saved machine that is not watched keeps whatever it last said, and gets its glyph the first time it is watched, or the user can pick it. Probing every machine at once would mean a connection to each, which Paddock does not hold.
- **The icon changes no behaviour.** Wake capture, alerts and the terminal do not read it (`HostOs` says so in its first paragraph), so a wrong answer costs a glyph and nothing else. The wake capture's Linux and Mac commands are chosen by what the capture finds on the host, as before.

## Watch another machine (Pro, `hosts.switch`)

`ProCapabilities.SWITCH_MACHINE` ("Switching between saved machines"), in M8's "several hosts" and `hosts.merged` (the counts on the chips, below). It supersedes the vault's earlier "a machine picker is a Free fix". A phone without Pro sees **Watch** with the lock glyph and the "Pro" tag (`PaddockButton(pro = true)`; TalkBack reads "Watch Beta server · Pro"), and a lock on the other machines' chips on Home; the tap asks the gate (`requestCapability`): the sheet from an idle app, a one-sentence notice from a pending answer, Manual input or an operation in flight, and nothing is switched. With Pro the tap calls `watchProfile(id, chosen = true)` (the method an alert already used, which calls it with the default `chosen = false`), which saves the choice, replaces the controller and says "Watching <name>." Free is still: adding a machine, removing one, waking any of them, going back to the chosen machine (below), and the switch an **alert** makes (tapping an alert for another saved machine), because alerts are Free. A Free user can also watch a saved machine again by adding it again (the same address updates it and makes it the watched one): the add form is not gated, and Paddock does not pretend otherwise.

### The chosen machine

The machine the user last chose **themselves** is the chosen machine (`AppSettings.chosenProfileId`), as opposed to the one an alert moved the phone to, and going back to it is always Free. Without this, an alert from machine B moved a Free phone to B and going back to A was Pro, so a Free user with two machines was watched by whichever machine alerted last.

- **What sets it:** adding a machine (it is watched and chosen; setting up the watched machine's key from Home's "Set up key" or "Show the command" is not adding one, so it leaves the choice where it was, `MachineRoster.choosesOnAdd`: fixing the key of the machine an alert moved the phone to must not take away the free return); Watch on the list, on a machine's page or a chip on Home (`watchProfile(id, chosen = true)`, Pro or a free return); the fallback when Remove takes the watched machine (the next machine, which the confirmation named, is watched and chosen); removing the chosen machine while another is watched (the watched one becomes the choice); and start-up, when the field is missing (settings written before it existed) or names a machine that no longer exists: it becomes the watched machine's id and is saved once (`MachineRoster.startupChoice`). Never from a list that could not be read or read no machine: that says nothing about which machines exist, and saving from it would write "no choice" over one that is still good.
- **What never sets it:** an alert. `resolveAlert` and `resolveMachine` reach `freshHerd`, which calls `watchProfile(id)` with `chosen = false`: the phone watches the alert's machine and the choice stays where it was.
- **What the list says:** the chosen machine, when it is not the watched one, is a `MachineRow.returnFree` row. Its Watch never carries the lock or the "Pro" tag (nor does its TalkBack label), its chip on Home has no lock, and a phone without Pro sees a dim line under the intro, `MachineCopy.displaced`: "An alert moved this phone to <watched>. Returning to <chosen> is free." With Pro, every Watch is open and the line is not shown.
- **What the tap does:** one function for the chip row, the list and the page (`switchMachine` in `PaddockRoot.kt`, deciding by `MachineSwitch.decide`) skips the gate for a `returnFree` row (no `requestCapability`, so no sheet and no deferral notice) and asks it for every other row while the switch is locked; a locked row's tap switches nothing (the sheet, or the gate's own sentence when busy). Whatever the gate allows still waits for an operation in flight (`MachineCopy.SWITCH_BUSY`), then calls `watchProfile(row.id, chosen = true)` and says "Watching <name>." (`MachineCopy.nowWatching`). That notice, "Removed <name>." and the busy sentence are in the notice bar, whose sentence is a polite live region, so TalkBack reads them when they appear.

## Remove a machine (Free)

**Remove…** is on the machine's page only (TalkBack: "Remove Beta server…"). It asks first (`ConfirmDialog`, danger): the title names the machine, the body says what happens to the watched machine ("Paddock then watches <next>", where next is `MachineRoster.after`: the chosen machine when it is another saved one, else the first of the others by name; or "has no machine to watch and asks you to add one"), and three facts (`MachineCopy.REMOVE_FACTS`) say what is forgotten, what is kept and what is left alone. After a removal the app says "Removed <name>." and returns to Machines; with no machine left it opens Welcome, then Add a machine. The removal runs in the graph's scope (`AppGraph.requestRemoval`), and both what it is doing and what it came to are the graph's state, not the page's: `removingMachine` keeps Watch and Remove… waiting, and `removalOutcome` holds the result until the root has shown it, so a rotation or a trip away during a removal neither re-enables them early nor loses the notice.

| | |
| --- | --- |
| Forgotten | the profile (name, address, port, user, session, wake facts and relay), the trusted host key (`FileHostKeyStore.remove`, and the broker's changed-key and pairing-fingerprint records), the ledger's observations, acknowledgements and actions for it (`Ledger.forgetHost`), its alert registration (`UnifiedPushConnector.unregister`, so the distributor is told), the widgets' copy of it when that is the machine the cache holds (`WidgetCacheStore.clear`: the cache carries agent titles), and a pairing request made for its address |
| Kept | the operation journal and saga rows (what the phone sent; no machine text, and the journal's rule is that an unknown outcome is never deleted: adding the same machine again finds it), this phone's own key, the one imported key (every machine shares it; Import key manages it), the ledger's epoch counters (an epoch is never handed out twice on this phone; a counter is a host id, a session name and a number), snippets and settings |
| On the machine | nothing. The key this phone put in `~/.ssh/authorized_keys` stays until the owner deletes its `paddock@phone` line, and an alert relay set up there keeps its settings (taking it down needs a connection to the machine, which Remove does not make); the dialog says both |

`MachineRemoval` runs the forgetting first and the profile **last**, each step safe to run twice. A step that fails leaves the profile listed and names the step; every other step has already run, so the notice says the machine is partly forgotten ("…The rest is already forgotten, so it stays listed, will ask you to trust it again, and its alerts are off. Try Remove again."), and a half-removed machine never sits unlisted with its secrets. Add, switch and remove are serialized (`AppGraph.machineLock`), and the machine being removed is refused by `watch` for the whole removal (a foreground flip does `watch(_profile.value)` and the removed machine is still that until the end) and its connection is dropped at once (`ConnectionOwner.drop`, no 8-second grace in which a reconnect could ask to trust a key just forgotten). A widget refresh job that started before the removal clears the cache again when it notices. Watch on the list and the page, and the page's Remove, wait while a removal runs, and a switch waits for an operation in flight ("An operation on this machine is still running. Switch once it finishes.": leaving a machine ends what runs on it as unknown). Removing the watched machine stops watching it before anything is deleted (so nothing it writes comes after), then watches the chosen machine when it is another saved one (an alert may have moved the phone off it), else the first remaining machine by name, as at start-up, or none: the app then opens Add a machine. Its Wake facts go with it (`MachineWake.forget`). `HostUiModel.reset` drops the last herd it showed, so the same machine added again does not come back with its old rows.

## Found by review (2026-10-06) and fixed

An independent read of the diff found: Remove and Watch could run at once (a removal confirmed while another was running could leave a deleted machine watched and connected); a foreground flip during a removal re-watched the machine being removed and its controller wrote ledger rows and the widget cache after they were forgotten; the connection owner's grace let a reconnect raise a first-trust prompt for a forgotten key; a widget job that started earlier could write the removed machine's cache back; the dialog said "opens Add a machine" where Welcome opens after a restart; a partly failed Remove did not say the machine was already partly forgotten; the pairing step cancelled a request another saved machine on the same host still needed; "Not now" on one machine's relay prompt hid another machine's; a Pro holder's switch abandoned an operation in flight. Each has a fix above or in the code; the serialization and the foreground race are covered by `MachineRemovalGraphTest` only for the single-call paths, not for two removals racing (not tested).
