# Saved machines: watch another, remove one

Paddock saves every machine the user adds and **watches one at a time** (`AppSettings.watchedProfileId`). Adding a machine saves it and makes it the watched one, as before; adding the same host, port and user again updates that profile. This page is what the machine chip on Home adds (2026-10-06, the user's decisions): a list of the saved machines, **watch another one (Pro)** and **remove one (Free)**.

## The machine list

The chip on Home that names the watched machine (`HostChip`, with a small machine icon and a 48 dp target) opens **Machines** (`MachinesDialog`): one card for each saved machine with its name, `user@host:port` and session, the watched one marked **Watching**, and under the others a **Watch** button. Every card has **Remove…**. **Add another machine** is the same route as in Settings. Close is the focused choice. The list is `AppGraph.machines`, read from the profile store at start, after an add and after a removal; `MachineRoster.rows` puts the watched machine first.

## Watch another machine (Pro, `hosts.switch`)

`ProCapabilities.SWITCH_MACHINE` ("Switching between saved machines"), in M8's "several hosts" with the reserved `hosts.merged`. It supersedes the vault's earlier "a machine picker is a Free fix". A phone without Pro sees **Watch · Pro** (`proLabel`; TalkBack reads "Watch Beta server · Pro"); the tap closes the list and asks the gate (`requestCapability`): the sheet from an idle app, a one-sentence notice from a pending answer, Manual input or an operation in flight, and nothing is switched. With Pro the tap calls `watchProfile` (the method an alert already used), which saves the choice, replaces the controller and says "Watching <name>." Free is still: adding a machine, removing one, and the switch an **alert** makes (tapping an alert for another saved machine), because alerts are Free. A Free user can also watch a saved machine again by adding it again (the same address updates it and makes it the watched one): the add form is not gated, and Paddock does not pretend otherwise.

## Remove a machine (Free)

**Remove…** asks first (`ConfirmDialog`, danger): the title names the machine, the body says what happens to the watched machine ("Paddock then watches <next>" or "has no machine to watch and asks you to add one"), and three facts (`MachineCopy.REMOVE_FACTS`) say what is forgotten, what is kept and what is left alone.

| | |
| --- | --- |
| Forgotten | the profile (name, address, port, user, session, wake facts and relay), the trusted host key (`FileHostKeyStore.remove`, and the broker's changed-key and pairing-fingerprint records), the ledger's observations, acknowledgements and actions for it (`Ledger.forgetHost`), its alert registration (`UnifiedPushConnector.unregister`, so the distributor is told), the widgets' copy of it when that is the machine the cache holds (`WidgetCacheStore.clear`: the cache carries agent titles), and a pairing request made for its address |
| Kept | the operation journal and saga rows (what the phone sent; no machine text, and the journal's rule is that an unknown outcome is never deleted: adding the same machine again finds it), this phone's own key, the one imported key (every machine shares it; Import key manages it), the ledger's epoch counters (an epoch is never handed out twice on this phone; a counter is a host id, a session name and a number), snippets and settings |
| On the machine | nothing. The key this phone put in `~/.ssh/authorized_keys` stays until the owner deletes its `paddock@phone` line, and an alert relay set up there keeps its settings (taking it down needs a connection to the machine, which Remove does not make); the dialog says both |

`MachineRemoval` runs the forgetting first and the profile **last**, each step safe to run twice. A step that fails leaves the profile listed and names the step; every other step has already run, so the notice says the machine is partly forgotten ("…The rest is already forgotten, so it stays listed, will ask you to trust it again, and its alerts are off. Try Remove again."), and a half-removed machine never sits unlisted with its secrets. Add, switch and remove are serialized (`AppGraph.machineLock`), and the machine being removed is refused by `watch` for the whole removal (a foreground flip does `watch(_profile.value)` and the removed machine is still that until the end) and its connection is dropped at once (`ConnectionOwner.drop`, no 8-second grace in which a reconnect could ask to trust a key just forgotten). A widget refresh job that started before the removal clears the cache again when it notices. The list's Watch and Remove wait while a removal runs, and a switch waits for an operation in flight ("An operation on this machine is still running. Switch once it finishes.": leaving a machine ends what runs on it as unknown). Removing the watched machine stops watching it before anything is deleted (so nothing it writes comes after), then watches the first remaining machine by name, as at start-up, or none: the app then opens Add a machine. `HostUiModel.reset` drops the last herd it showed, so the same machine added again does not come back with its old rows.

## Tests

- `core`: `ConnectionOwnerTest` (`drop` closes at once and nothing reconnects a dropped machine), `MachinesTest` (the list order, the dialog's sentences, every step before the profile, a failing step keeps the profile and names itself, several failures, a second try finishes, cancellation is not swallowed), `LedgerTest` (forgetting a host drops only its facts; an epoch is never reused), `ProGateTest` (`hosts.switch` is gated; removing is not), `ProCopyTest`.
- `app` unit: `ButtonRolesTest` (Watch Secondary, Remove… Danger, Add another machine Ghost).
- Instrumentation: `MachinesTest` (every machine listed, the watched one marked, a locked Watch says "· Pro" and still reaches the caller, Remove is never locked, 200% font, the accessibility audit dark and light, the chip opens the list only when given somewhere to go).
- Not run on a phone: the whole flow with two real machines (switch, then Remove of the watched one, then Remove of the last one).

## Found by review (2026-10-06) and fixed

An independent read of the diff found: Remove and Watch could run at once (a removal confirmed while another was running could leave a deleted machine watched and connected); a foreground flip during a removal re-watched the machine being removed and its controller wrote ledger rows and the widget cache after they were forgotten; the connection owner's grace let a reconnect raise a first-trust prompt for a forgotten key; a widget job that started earlier could write the removed machine's cache back; the dialog said "opens Add a machine" where Welcome opens after a restart; a partly failed Remove did not say the machine was already partly forgotten; the pairing step cancelled a request another saved machine on the same host still needed; "Not now" on one machine's relay prompt hid another machine's; a Pro holder's switch abandoned an operation in flight. Each has a fix above or in the code; the serialization and the foreground race are covered by `MachineRemovalGraphTest` only for the single-call paths, not for two removals racing (not tested).
